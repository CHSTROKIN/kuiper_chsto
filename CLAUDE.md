# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

An educational C++/CUDA LLM inference engine, derived from KuiperInfer and KuiperLLama. It holds two independent codebases with very different states.

## `llama3_kernels/`: self-contained, builds and runs

Needs only C++17, the CUDA toolkit, CMake ≥ 3.18 and optionally OpenMP. Run from the repo root:

```bash
cmake -S llama3_kernels -B build_kernels -DCMAKE_BUILD_TYPE=Release   # add -DCMAKE_CUDA_ARCHITECTURES=89 to build only for an RTX 40xx
cmake --build build_kernels -j
./build_kernels/test_kernels                 # or: ctest --test-dir build_kernels
./build_kernels/llama3_forward --model tiny  # also 1b; 8b needs --layers 2 on an 8 GB GPU
./build_kernels/bench_kernels --model 1b
./build_kernels/chat                         # needs weights in models/ (download: llama3_kernels/README.md §0)
```

`test_kernels` is a plain program, not GTest, and takes no arguments, so there is no test filter. To run one test, temporarily comment out the other calls in `main()` of `apps/test_kernels.cpp`.

Design rules:
- `llama3::cpu` and `llama3::cuda` expose the same function names, arguments and shapes on raw `float*` (see the two `*_kernels.h` headers). CUDA versions also take a stream and are asynchronous, except `argmax`. Change both sides together.
- The CPU version is the reference. It is checked against hand-computed answers, and each CUDA kernel is compared with it.
- Readability comes before speed. Each source file starts with a comment explaining the math and, for CUDA, the thread mapping.
- `include/llama3/model.h` composes the kernels into `CpuLlama3` and `CudaLlama3`, shared by `apps/llama3_forward.cpp` (random weights, so meaningless token ids) and `apps/chat.cpp` (real weights).
- Real models are Hugging Face folders: `src/checkpoint.cpp` (config and safetensors, widened to fp32) and `src/tokenizer.cpp` (BPE, with the Llama 3 split pattern hand-written). There are no third-party dependencies, so JSON is parsed by `src/json.cpp`. `src/unicode_tables.h` is generated by `scripts/gen_unicode_tables.py`.
- `test_kernels` does not cover the loader, tokenizer or chat. After changing them, compare token ids and logits with Hugging Face `tokenizers` and `transformers`.
- With `OMP_NUM_THREADS` unset, the apps use half the logical CPUs. Using all of them can be much slower.

`docs/KERNELS.md` explains the data layout (§3), each kernel, and performance.

## Main framework (`source/`, `include/`): does not currently build

```bash
cmake -S . -B build -DUSE_CPM=ON     # downloads dependencies
cmake --build build -j
```

- With `USE_CPM=OFF` (the default), compilation fails on the missing `absl/...` headers included by `include/op/encode.h`.
- Per `docs/KERNELS.md` §10, enabling CPM is not enough to get a working build: many declared classes (`op::Layer`, the concrete layers, `model::Model`, `sampler::ArgmaxSampler`, `RawModelData*`) have no implementation. `source/model/model.cpp` and `source/op/kernel.cpp` are placeholder stubs, and `model.cpp` defines `main()` inside the shared library. §10 also lists known kernel bugs.
- The root `CMakeLists.txt` hardcodes `nvcc` at `/usr/local/cuda/bin/nvcc`, and `cmake/cuda.cmake` sets the CUDA architectures from the detected GPU.
- Targets are `llama` (shared library, output to `lib/`), `llama_infer` (from `demo/main.cpp`, arguments: checkpoint path, then tokenizer path) and `test_llm` (GTest; once it builds, filter with `--gtest_filter=Suite.Name`).
- `README.md`, `docs/ARCHITECTURE.md` and `docs/API_REFERENCE.md` describe intended behavior. Check claims against the source. For example, the README's `./bin/demo` does not match the target name.

Intended layering: `model::LLama2Model` (`source/model/llama3.cpp`) builds `op::Layer` objects and runs, for each transformer layer, RMSNorm → QKV matmuls and RoPE → MHA with KV cache → feed-forward, then the final logits. Layers operate on `tensor::Tensor`, whose memory comes from a `base::DeviceAllocator` (the CUDA one pools buffers). They dispatch by `DeviceType` through the function-pointer getters in `source/op/kernels/kernels_interface.h` to the `cpu/` or `cuda/` implementation. The CUDA MHA is a single fused kernel.

The two codebases share no code. `llama3_kernels/` can serve as the reference when fixing framework kernels.

## Stray build artifacts

An old in-source build left `Makefile`, `CMakeCache.txt`, `CMakeFiles/`, `_deps/` and similar at the repo root, and `lib/` holds old binaries. All are gitignored, and their presence says nothing about whether the current source builds. Always build out of source with `-B`.
